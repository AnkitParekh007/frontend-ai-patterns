# Architecture Decision Records — Frontend AI Patterns

## ADR-001 — Model AI interaction as typed UI state

**Context:** streaming, retrieval, tool work and approvals are asynchronous and can fail independently.

**Decision:** define explicit TypeScript contracts/state for intermediate AI behavior instead of deriving UX from ad-hoc booleans or raw provider events.

**Alternatives:** render provider payloads directly; keep only `loading/success/error`.

**Consequences:** more state modeling, but deterministic rendering, accessibility and testing improve substantially.

## ADR-002 — Keep citations as first-class product data

**Context:** grounded AI output is only useful when users can inspect evidence.

**Decision:** represent citations/source metadata separately from assistant prose and preserve source availability/failure state.

**Alternatives:** inline plain-text links generated by the model; hide retrieval details.

**Consequences:** the frontend must handle source-card state, but grounding becomes inspectable and testable.

## ADR-003 — Make tool execution visible

**Context:** an agent that silently executes tools creates ambiguity about what changed and why.

**Decision:** render tool planning/execution as a timeline with distinct pending, approval, executing, success and failure states.

**Alternatives:** show only final assistant prose.

**Consequences:** UI complexity increases, while user trust and operational debugging improve.

## ADR-004 — Treat approval UX as a view over backend policy

**Context:** human approval is useful only when protected work is actually blocked behind it.

**Decision:** frontend patterns collect and render approval state, but documentation explicitly requires backend enforcement for consequential actions.

**Alternatives:** client-only confirmation dialogs.

**Consequences:** examples remain honest about the security boundary and can be adapted to different backend systems.

## ADR-005 — Prefer framework-neutral contracts with Angular reference implementations

**Context:** the architectural ideas should travel across stacks, while the portfolio benefits from deep Angular expertise.

**Decision:** keep core contracts JSON-serializable/TypeScript-first; maintain Angular as the primary implementation reference; add other framework examples only where they prove portability.

**Consequences:** the repo can attract broader usage without becoming a lowest-common-denominator UI framework.
